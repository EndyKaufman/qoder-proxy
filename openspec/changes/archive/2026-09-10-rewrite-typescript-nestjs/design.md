## Контекст

См. [proposal.md](proposal.md) — мотивация. Текущий проект — ~1500 строк JavaScript в 11 исходных файлах + ~1500 строк тестов (7 integration + 7 unit suites, 167 тестов). Integration-тесты уже на TypeScript, unit-тесты ещё на JS. Переписывание должно сохранить каждую конечную точку API, форму ответа, поведение стриминга и формат ошибок в точности как есть.

## Цели / Не-цели

**Цели:**
- Типобезопасная кодовая база со строгим TypeScript (`strict: true`)
- Плоская структура NestJS с одним AppModule — без отдельных feature-модулей
- Идентичное внешнее поведение API (все конечные точки, стриминг, SSE, форматы ошибок)
- Внедрение зависимостей только там, где есть реальное переиспользование
- Swagger-документация через OpenAPI-декораторы на всех DTO
- Статический фронтенд дашборда отдаётся без изменений

**Не-цели:**
- Добавление новых конечных точек API или функций
- Переписывание фронтенда дашборда (HTML/JS/CSS остаётся как есть)
- Добавление базы данных или персистентного хранилища (in-memory logStore остаётся in-memory)
- Написание новых тестов (существующие 167 тестов мигрируют на TS, но новые не добавляются)
- Изменение имён переменных окружения или добавление новых

## Решения

### 1. Структура: один AppModule, плоская организация

```
src/
├── main.ts                          # Bootstrap + Swagger setup
├── app.module.ts                    # Единственный модуль: импорты, провайдеры, контроллеры
├── app.controller.ts                # GET / (root info), GET /health
├── chat.controller.ts               # POST /v1/chat/completions, GET /v1/chat/completions
│                                    # DTO с @ApiProperty() прямо в файле контроллера
│                                    # Логика стриминга — прямо в контроллере (не дублируется)
├── completions.controller.ts        # POST /v1/completions
│                                    # DTO прямо в файле контроллера
├── models.controller.ts             # GET /v1/models, POST /v1/embeddings (501), catch-all
├── dashboard.controller.ts          # Все маршруты /dashboard/*
├── common/
│   ├── guards/
│   │   ├── api-key.guard.ts         # Bearer token auth
│   │   └── dashboard-auth.guard.ts  # Cookie-based auth
│   ├── middleware/
│   │   └── logger.middleware.ts     # Логирование запросов
│   └── filters/
│       └── global-exception.filter.ts
├── config/
│   └── configuration.ts             # Типизированная фабрика (без отдельного модуля)
├── qoder-cli/
│   ├── qoder-cli.service.ts         # Spawn-логика (используется chat + completions + dashboard + health)
│   └── qoder-cli.models.ts          # Каталог моделей + алиасы (используется chat + models + dashboard)
├── log-store/
│   └── log-store.service.ts         # In-memory логи (используется logger middleware + dashboard + qoder-cli)
└── utils/
    ├── format.ts                    # messagesToPrompt, extractTextContent, newId, response builders
    └── tool-prompt.ts               # Tool call prompt injection + parsing
```

**Принцип «сервисы только при реальном переиспользовании»:**

Сервис создаётся только если его логика вызывается из **двух и более** мест:
- `QoderCliService` — используется из `chat.controller`, `completions.controller`, `dashboard.controller`, `app.controller` (health) ✓
- `LogStoreService` — используется из `logger.middleware`, `dashboard.controller`, `qoder-cli.service` ✓
- ~~ChatService~~ — вызывается только из `ChatController` → логика остаётся в контроллере
- ~~CompletionsService~~ — вызывается только из `CompletionsController` → логика остаётся в контроллере
- ~~DashboardService~~ — вызывается только из `DashboardController` → логика остаётся в контроллере

**Принцип «DTO в контроллерах»:**

DTO/интерфейсы запросов и ответов определяются прямо в файле контроллера, если не переиспользуются за его пределами. Все DTO имеют декораторы `@ApiProperty()` из `@nestjs/swagger` для автоматической Swagger-документации. Общие типы (например, `ErrorResponse`) выносятся в `common/` только если используются в нескольких контроллерах.

**Обоснование**: Проект на ~1500 строк — создание feature-модулей (ChatModule, CompletionsModule и т.д.) добавляет boilerplate без пользы. Один AppModule с плоской структурой проще навигировать, легче понять зависимости. Сервисы-прокси (контроллер → сервис → та же логика) — антипаттерн, увеличивающий количество файлов без снижения сложности.

**Рассмотренные альтернативы**:
- _Feature-модули (ChatModule, CompletionsModule, ...)_ : Стандартный подход NestJS, но избыточен для проекта такого размера. Каждый модуль = 3 файла (module, controller, service), где сервис — просто прокси.
- _CQRS / сложные паттерны_: Полностью не оправданы для прокси-сервера.

### 2. Подход к стримингу

Использовать сырой Express `Response` через `@Res()` в контроллерах NestJS для SSE-стриминга. Стандартная обработка ответов NestJS перехватывает response, поэтому стриминг требует явного отказа через `@Res({ passthrough: false })`.

**Обоснование**: Текущая логика стриминга тесно связана с Express `res.write()` / `res.end()`. Декоратор `@Sse()` в NestJS поддерживает только простые паттерны событий и не обрабатывает сложный многофазный стриминг (role chunk → content chunks → tool call chunks → done), необходимый здесь. Прямой доступ через `@Res()` сохраняет полный контроль.

**Рассмотренные альтернативы**:
- _Декоратор `@Sse()` в NestJS_: Слишком ограничен для многофазного SSE с условными типами чанков.
- _Потоковая обработка через RxJS Observable_: Добавляет сложность без выгоды, так как источник данных — дочерний процесс, а не observable-поток.

### 3. Валидация конфигурации

Использовать `@nestjs/config` с фабричной функцией `configuration.ts`, которая читает `process.env` и возвращает типизированный объект. Добавить runtime-валидацию через `class-validator` на классе `EnvironmentVariables` для быстрого падения при отсутствующих/невалидных переменных окружения.

**Обоснование**: Соответствует текущему поведению `config.js` (читает env, применяет defaults, экспортирует объект), добавляя типовую безопасность и валидацию. Текущий код использует `parseInt` с fallback и ручные проверки null — типизированная фабрика сохраняет этот паттерн.

### 4. Стратегия auth guard

Реализовать `ApiKeyGuard` как NestJS guard, применяемый на уровне контроллера для маршрутов `/v1/*`. Guard читает `PROXY_API_KEY` из `ConfigService` и пропускает auth, если не установлен (соответствуя текущему поведению).

**Обоснование**: Guard'ы — это идиоматический эквивалент Express middleware для auth в NestJS. Применение на уровне контроллера (не глобально) соответствует текущему паттерну, где только маршруты `/v1/*` требуют auth.

### 5. Инструментарий сборки

Использовать `@nestjs/cli` (`nest build`) с компилятором `tsc`. Вывод в `dist/`. Конфиг `nest-cli.json` указывает `src/` как корень исходников.

**Обоснование**: `@nestjs/cli` — стандартный инструмент сборки NestJS. Использование `tsc` (не `swc` и не `webpack`) делает сборку простой и предсказуемой для проекта такого размера.

**Рассмотренные альтернативы**:
- _`tsup` или `esbuild`_: Быстрее, но нестандартно для NestJS, возможны проблемы с декораторами и `reflect-metadata`.
- _`swc`_: Быстрее, но добавляет сложность без существенной выгоды на таком масштабе.

### 6. Статические файлы дашборда

Продолжить отдавать `src/dashboard/public/` как статические ресурсы через `@nestjs/serve-static` или Express `express.static` middleware, зарегистрированный в AppModule.

**Обоснование**: Фронтенд (HTML/JS/CSS) вне рамок. Простейший подход — отдавать ту же директорию с того же URL-префикса.

### 7. Swagger-документация

Подключить `@nestjs/swagger` для автоматической генерации OpenAPI-документации. В `main.ts` настроить `SwaggerModule.setup('api/docs', app, document)`.

Все DTO в контроллерах используют декораторы `@ApiProperty()`, `@ApiPropertyOptional()`, `@ApiResponse()` для описания запросов и ответов. Контроллеры декорируются `@ApiTags()`, `@ApiOperation()`, `@ApiResponse()`.

Зависимость `@nestjs/swagger` добавляется в package.json. Swagger UI доступен по `/api/docs` в development-режиме.

**Обоснование**: OpenAPI-документация позволяет клиентам и IDE автоматически обнаруживать доступные эндпоинты, форматы запросов/ответов. Декораторы живут прямо на DTO — нет отдельного файла спецификации, который рассинхронизируется с кодом.

### 8. Миграция тестов на TypeScript

7 unit-тестов (`tests/unit/helpers/{format,spawn,toolPrompt}.test.js`, `tests/unit/middleware/{auth,dashboardAuth,logger}.test.js`, `tests/unit/store/logStore.test.js`) переписываются на TypeScript. Integration-тесты (8 файлов) уже на TS и не требуют изменений.

`ts-jest` и `typescript` уже установлены. Jest настроен на поддержку обоих форматов. `tsconfig.json` уже существует, но покрывает только `tests/**/*.ts` — его нужно расширить для `src/**/*.ts` с `outDir: dist`, `emitDecoratorMetadata: true` и другими NestJS-требованиями.

При миграции unit-тестов:
- Заменить `require()` на типизированные `import` из новых TS-модулей (например, `import { getModelMapping } from '../../src/qoder-cli/qoder-cli.models'`, `import { messagesToPrompt } from '../../src/utils/format'`).
- Обновить `jest.mock()` пути с `.js` на `.ts` модули.
- Добавить типы для моков и тестовых данных.
- Удалить старые `.test.js` файлы после создания `.test.ts` аналогов.

**Обоснование**: Типизированные тесты дают дополнительную проверку контрактов при компиляции. После переписывания основного кода на TS, `require()` из JS-тестов не сможет корректно импортировать из TS-модулей без дополнительной конфигурации. Миграция тестов — необходимая часть, а не опциональная.

## Риски / Компромиссы

- **[Точность стриминга]** → Логика SSE-стриминга — самая сложная часть кодовой базы. Прямое использование `@Res()` сохраняет полный контроль, но миграция должна тщательно воспроизвести каждый тип чанка, поведение flush и обработку отключения клиента. **Митигация**: Сохранить логику стриминга структурно идентичной; протестировать с реальными IDE-клиентами (Continue, Zed) после миграции.

- **[Время запуска]** → NestJS имеет более медленный холодный старт, чем raw Express, из-за разрешения модулей и рефлексии. **Митигация**: Приемлемо для прокси-сервера, работающего непрерывно. Docker health check `start-period` уже допускает 15 секунд.

- **[Размер бандла]** → NestJS добавляет ~10-15 МБ в `node_modules` по сравнению с текущими ~5 МБ. **Митигация**: Важно только в Docker; образ `node:20-slim` имеет достаточно места.

- **[Риск миграции]** → Переписывание всех файлов за раз — это big-bang изменение без постепенного отката. **Митигация**: Переписывание механическое (отображение 1:1). Хранить старые файлы `src/`, пока новая сборка не проверена, затем удалить. Dockerfile можно обновить для отката на старую точку входа при необходимости во время перехода.

- **[Метаданные декораторов]** → NestJS требует `emitDecoratorMetadata: true` в tsconfig и импорт `reflect-metadata`. Пропуск этого вызывает тихие сбои DI. **Митигация**: Задокументировать в комментариях tsconfig; добавить `import 'reflect-metadata'` в начало `main.ts`.
