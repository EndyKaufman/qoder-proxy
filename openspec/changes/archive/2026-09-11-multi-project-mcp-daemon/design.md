## Context

См. proposal.md. Текущая архитектура: NestJS-прокси спавнит `qodercli` на каждый запрос через `child_process.spawn`, убивает после ответа. qodercli работает в директории прокси, без MCP. Необходимо перейти на персистентный демон `qodercli remote-control` с поддержкой множества проектов и MCP-серверов.

Ключевые ограничения:
- `qodercli remote-control` создаёт Unix socket `/tmp/qoder-{PID}.sock`
- Протокол сокета требует исследования (предположительно HTTP-over-Unix-socket или JSON-RPC)
- MCP npm-пакеты требуют `npx` и интернет для первого запуска
- Конфиги проектов должны быть доступны через volume в Docker

## Goals / Non-Goals

**Goals:**
- Персистентный демон qodercli (без спавна на каждый запрос)
- Множество проектов с независимыми подключениями к сервисам
- Распознавание проектов по упоминанию в тексте (включая алиасы)
- Мульти-проектные операции (сравнение, копирование между проектами)
- Обратная совместимость API (формат запросов не меняется)
- Горячая перезагрузка конфигов проектов

**Non-Goals:**
- Изменение формата OpenAI-совместимого API
- Поддержка embedding-эндпоинтов с MCP
- Управление проектами через API (только через YAML-файлы)
- Веб-интерфейс для управления конфигами проектов
- Поддержка Windows (только Linux в Docker)

## Decisions

### 1. Один демон на все проекты vs per-project демоны

**Решение:** Один `qodercli remote-control` демон с `--directory /projects` (корень всех проектов).

**Обоснование:** Мульти-проектные операции (сравнение БД, копирование файлов) требуют одновременного доступа к нескольким проектам. Один демон с общим MCP JSON видит все серверы. Per-project демоны потребовали бы координации между ними.

**Альтернатива:** Per-project демоны с проксированием запросов между ними. Отклонено: избыточная сложность, проблемы с межпроектными операциями.

### 2. Формат конфигов проектов: YAML vs JSON vs .env

**Решение:** YAML.

**Обоснование:** YAML удобочитаем для людей, поддерживает вложенные структуры (postgres: {host, port, ...}), стандарт для Docker/K8s экосистемы. JSON менее читаем, .env не поддерживает вложенность.

**Альтернатива:** JSON -- отклонён из-за читаемости. .env -- отклонён из-за отсутствия вложенности.

### 3. Протокол коммуникации с демоном

**Решение:** Использовать Unix socket демона. Протокол требует исследования на этапе реализации. Вероятные варианты:
- HTTP-over-Unix-socket (если демон экспортирует HTTP API)
- JSON-RPC over Unix socket
- Прямое подключение через `--remote-control <id>` worker mode

**Обоснование:** `qodercli remote-control` уже создаёт `/tmp/qoder-{PID}.sock`. Node.js `net` модуль поддерживает Unix socket natively.

**Риск:** Протокол может быть недокументирован. Митигация: исследовать исходный код qodercli или использовать fallback на stdin/stdout interactive mode.

### 4. Горячая перезагрузка конфигов

**Решение:** File watcher на директории `PROJECTS_CONFIG_DIR` (chokidar или fs.watch). При изменении -- перечитать YAML, перегенерировать MCP JSON, перезапустить демон.

**Обоснование:** Позволяет добавлять/менять проекты без перезапуска контейнера. chokidar -- стандартная библиотека для Node.js file watching.

**Альтернатива:** Polling каждые N секунд. Отклонено: менее эффективно, задержка реакции.

### 5. Fallback при отсутствии remote-control протокола

**Решение:** Если протокол Unix socket демона не поддаётся интеграции, использовать fallback: персистентный `qodercli -i` (interactive mode) с stdin/stdout pipe на проект. Один процесс на запрос, но с сохранением контекста через `--resume`.

**Обоснование:** Гарантирует работоспособность даже без поддержки remote-control протокола.

### 6. Структура исходного кода

**Решение:** Новые сервисы в отдельных директориях:
- `src/project-config/project-config.service.ts` -- загрузка и валидация YAML
- `src/mcp-gen/mcp-gen.service.ts` -- генерация MCP JSON
- `src/daemon/daemon.service.ts` -- lifecycle демона и коммуникация

**Обоснование:** Следует существующей архитектуре проекта (flat structure, один AppModule). Каждый сервис инкапсулирует свою область.

### 7. Зависимость yaml-парсера

**Решение:** Использовать пакет `yaml` (npm) -- поддерживает YAML 1.2, TypeScript types, без нативных зависимостей.

**Альтернатива:** `js-yaml` -- тоже популярен, но `yaml` имеет лучшую типизацию.

### 8. Клонирование репозиториев

**Решение:** Использовать `git clone` через `child_process.execFile` (не MCP). При загрузке конфига с `github_url` -- если `path` не существует, клонировать; если существует и это git -- `git pull`. Поддержка `url#branch` через парсинг фрагмента.

**Обоснование:** `git clone` -- стандартная операция, не требует MCP. Простая и надёжная. qodercli уже имеет git-summary-mcp для работы с git внутри проекта.

**Альтернатива:** GitHub MCP (`@modelcontextprotocol/server-github`) -- отклонён: требует токен, а пользователь хочет публичные репо.

### 9. Headless-браузер

**Решение:** Добавить `@playwright/mcp` как глобальный MCP-сервер (без префикса проекта) в генерируемый MCP JSON. Docker-образ строится на базе с Chromium (`mcr.microsoft.com/playwright` или установка зависимостей).

**Обоснование:** Playwright MCP уже существует, поддерживает навигацию, скриншоты, file upload/download. Глобальный (не привязан к проекту) -- браузер один на все проекты.

**Альтернатива:** Puppeteer MCP -- менее функционален. Собственный headless-сервис -- избыточная сложность.

### 10. Webhook callback

**Решение:** Новая `src/webhook/webhook.service.ts` с методом `sendWebhook(url, payload)`. Контроллеры передают `webhook_url` из запроса в сервис обработки, который после завершения вызывает webhook. Повторные попытки через простой цикл с `setTimeout`.

**Обоснование:** Простая реализация, не требует внешних зависимостей. `fetch` (Node.js built-in) для HTTP-запросов. Экспоненциальная задержка -- стандартный паттерн.

**Альтернатива:** Очередь задач (Bull/BeeQueue) -- отклонено: избыточно для одного webhook, добавляет зависимость от Redis.

### 11. Мини-приложения (дашборды)

**Решение:** Динамический Express router внутри NestJS. Каждый дашборд -- директория в `DASHBOARD_APPS_DIR` с `index.html` + опциональный `controller.js`. При старте и при изменении директории (file watcher) система сканирует поддиректории и регистрирует маршруты на `/dashboard-apps/:appName/*`. Controller.js экспортирует `{ routes: [...], setupStream? }`. Доступ к данным -- через глобальный реестр подключений (`getPgConnection`, `getRedisConnection` и т.д.), построенный на тех же connection strings что и MCP.

**Обоснование:** Express router -- самый простой способ динамической регистрации без перезапуска NestJS. File watcher обеспечивает hot-reload. Реестр подключений переиспользует те же connection strings, что и MCP-серверы -- нет дублирования.

**Альтернатива:** Генерация NestJS-контроллеров + перезапуск приложения -- отклонено: грубо, теряет сессии. Конфигурационный подход (YAML вместо кода) -- отклонено: недостаточно гибок, AI не может написать произвольную логику.

## Risks / Trade-offs

- **[Протокол сокета демона]** → Митигация: spike в первой задаче. Если протокол не поддаётся -- fallback на interactive mode (stdin/stdout pipe).
- **[Первый запуск MCP: npx скачивает пакеты]** → Митигация: pre-install в Dockerfile (`RUN npx -y @modelcontextprotocol/server-postgres --version` и т.д.) или init-контейнер.
- **[Демон может зависнуть]** → Митигация: health check + watchdog timer + автоматический restart.
- **[Большое количество MCP-серверов замедляет старт демона]** → Митигация: ограничение на количество проектов/сервисов, логирование времени старта.
- **[YAML-конфиги содержат пароли]** → Митигация: директория конфигов должна быть защищена; в Docker -- secret volume или environment variables для чувствительных данных.
- **[Aliased имена на разных языках]** → Митигация: регистронезависимое сравнение; AI сам распознаёт контекст по системному промпту.
- **[git clone может зависнуть на больших репо]** → Митигация: таймаут на операцию клонирования (5 минут), `--depth 1` для shallow clone по умолчанию.
- **[Playwright Chromium занимает много места в Docker]** → Митигация: использование `mcr.microsoft.com/playwright` base image или `playwright install --with-deps chromium` только chromium (не firefox/webkit).
- **[Webhook URL может быть недостижим]** → Митигация: 3 попытки с экспоненциальной задержкой, логирование после исчерпания.
- **[controller.js дашборда может содержать ошибки или небезопасный код]** → Митигация: sandbox через `vm2` или `isolated-vm` для запуска controller.js; ограничение доступа к файловой системе. На начальном этапе -- запуск в том же процессе с документированным API.
- **[Утечка подключений к БД при перерегистрации дашбордов]** → Митигация: пул подключений на уровне реестра (не на уровне дашборда), дашборд получает ссылку на общий пул.
