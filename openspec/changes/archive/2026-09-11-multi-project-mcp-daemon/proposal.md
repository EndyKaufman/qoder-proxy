## Почему

Текущая архитектура qoder-proxy запускает отдельный процесс `qodercli` на каждый API-запрос, убивая его после ответа. Это создаёт задержку на старт процесса и загрузку контекста. Кроме того, qodercli работает только в рамках одного проекта (текущая директория прокси) и не имеет доступа к внешним сервисам (PostgreSQL, Redis, MinIO, NATS, Docker). Пользователь, подключающийся из интернета, не может задать вопрос про сторонний проект, его базу данных, контейнеры или файлы.

Необходимо:
- Поддерживать множество сторонних проектов с собственными подключения к сервисам
- Позволять упоминать проекты по имени прямо в тексте запроса (включая операции с двумя проектами одновременно)
- Поддерживать алиасы имен проектов
- Держать qodercli в персистентном состоянии (демон) для устранения задержки старта
- Автоматически клонировать публичные репозитории с GitHub по URL
- Иметь headless-браузер для навигации по сайтам, скриншотов, отправки/приёма файлов
- Поддерживать webhook-уведомления: по завершении работы отправлять результат на указанный URL
- Создавать мини-приложения (дашборды) с агрегацией данных из различных источников, с генерацией кода (controller + HTML/JS) и динамической регистрацией без перезапуска сервера

## Что меняется

- Добавляется поддержка YAML-конфигов проектов: каждый файл описывает путь к коду, подключения к сервисам (PostgreSQL, Redis, MinIO, NATS, Docker) и алиасы имён
- Прокси при старте читает все конфиги, генерирует объединённый MCP JSON с префиксованными серверами (`pg_alpha`, `redis_beta` и т.д.) и системный промпт с каталогом проектов
- Вместо спавна/убийства `qodercli` на каждый запрос запускается персистентный демон `qodercli remote-control` с Unix socket, принимающий до 32 сессий
- Прокси общается с демоном через Unix socket (`/tmp/qoder-{PID}.sock`), отправляя промпты и получая ответы
- Поле `project` в API-запросе не требуется -- AI сам распознаёт упоминания проектов из текста
- Поддерживаются мульти-проектные операции: сравнение данных между БД, копирование файлов между проектами и т.д.
- YAML-конфиг проекта MAY содержать `github_url` -- публичный URL репозитория; система автоматически клонирует его в `path` при старте
- Добавляется MCP-сервер Playwright для headless-браузера: навигация, скриншоты, загрузка/скачивание файлов
- API поддерживает поле `webhook_url` в запросе; по завершении обработки прокси отправляет POST с результатом на этот URL
- AI-агент может создавать мини-приложения (дашборды): генерирует controller.js + HTML/JS для каждого, прокси регистрирует их динамически через Express router без перезапуска

## Возможности

### Новые
- `project-configs`: загрузка, валидация и управление YAML-конфигами проектов (путь, сервисы, алиасы)
- `mcp-generation`: генерация объединённого MCP JSON для всех проектов с префиксованными именами серверов
- `daemon-lifecycle`: запуск и управление персистентным демоном `qodercli remote-control` (старт, health check, restart)
- `daemon-communication`: отправка запросов и получение ответов через Unix socket демона
- `project-catalog-prompt`: генерация системного промпта с каталогом проектов и их алиасами для распознавания проектов AI
- `github-clone`: автоматическое клонирование публичных репозиториев GitHub по URL из конфига проекта
- `headless-browser`: headless-браузер (Playwright MCP) для навигации по сайтам, скриншотов, загрузки/скачивания файлов
- `webhook-callback`: отправка результата обработки запроса на указанный webhook URL
- `dashboard-apps`: создание, регистрация и управление мини-приложениями (дашбордами) с агрегацией данных из различных источников через динамический Express router

## Влияние

- **Код**: `src/config/configuration.ts` (новые env-переменные), `src/qoder-cli/qoder-cli.service.ts` (полная переработка: демон вместо спавна), новый `src/project-config/project-config.service.ts`, новый `src/mcp-gen/mcp-gen.service.ts`, новый `src/daemon/daemon.service.ts`
- **API**: формат запросов `/v1/chat/completions` и `/v1/completions` не меняется (обратно совместим); промпт обогащается системным контекстом проектов
- **Зависимости**: npm-пакеты MCP-серверов скачиваются через npx при первом запуске (postgres, redis, minio, nats, docker, git); yaml-парсер (`yaml` или `js-yaml`); Playwright MCP (`@playwright/mcp`) с браузерами Chromium
- **Docker**: образ должен содержать `npx` для запуска MCP-серверов, `git` для клонирования, Chromium для Playwright; volume для директории конфигов и проектов
- **Системные требования**: на целевой машине должны быть доступны сервисы (PostgreSQL, Redis, MinIO, NATS, Docker) по указанным в конфигах адресам
