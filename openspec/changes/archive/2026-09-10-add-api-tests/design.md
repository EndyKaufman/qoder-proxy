## Context

Проект — OpenAI-совместимый прокси на Express.js (Node.js), обёртка над `qodercli`. Текущий стек: JavaScript (CommonJS), Express 4, без тестов. Планируется миграция на TypeScript/NestJS. Для безопасной миграции необходим эталонный набор тестов, фиксирующий текущее поведение всех API. См. proposal.md для мотивации.

Ключевое ограничение: все тесты ДОЛЖНЫ работать без реального бинарника qodercli — вызовы `runQoderRequest` и `checkQoderCli` мокаются.

## Goals / Non-Goals

**Goals:**
- 100% покрытие всех HTTP-эндпоинтов интеграционными тестами (public + protected + dashboard)
- 100% покрытие всех вспомогательных функций и middleware юнит-тестами
- Тесты запускаются через `npm test` без внешних зависимостей
- Мокирование qodercli через Jest mock модулей (`jest.mock`)
- Тесты фиксируют текущее поведение как эталон для пост-миграционной валидации

**Non-Goals:**
- Покрытие веток (branch coverage) 100% — достаточно покрытия всех публичных API и основных путей
- Нагрузочное/стресс-тестирование
- E2E-тесты с реальным qodercli
- Изменение production-кода (только тесты + конфигурация)
- Настройка CI/CD pipeline (отдельная задача после миграции)

## Decisions

### 1. Jest + supertest вместо Mocha/Chai или Vitest
**Решение**: Использовать Jest как тестовый раннер и assertion library, supertest для HTTP-интеграционных тестов.
**Обоснование**: Jest — де-факто стандарт для Node.js-проектов, встроенный мокинг через `jest.mock()` идеально подходит для изоляции `runQoderRequest`/`checkQoderCli`. Supertest — стандарт для тестирования Express-приложений.
**Альтернативы**: Vitest (быстрее, но менее зрелый для CommonJS), Mocha + Chai (требует отдельной настройки мокинга).

### 2. Структура тестов: tests/integration/ и tests/unit/
**Решение**: Двухуровневая структура — `tests/integration/` для HTTP-тестов через supertest, `tests/unit/` для тестов отдельных модулей.
**Обоснование**: Чёткое разделение позволяет запускать юнит-тесты быстро (без создания HTTP-сервера) и интеграционные — для проверки полного стека.
**Альтернативы**: Плоская структура (проще, но сложнее масштабировать), зеркальная структура `src/` (избыточна для текущего размера проекта).

### 3. Мок qodercli через jest.mock на уровне модуля
**Решение**: `jest.mock('../../src/helpers/spawn')` — мок всего модуля spawn, с подменой `runQoderRequest` и `checkQoderCli`.
**Обоснование**: Интеграционные тесты не должны зависеть от реального бинарника. Мок на уровне модуля проще, чем инъекция зависимостей, и не требует изменения production-кода.
**Альтернативы**: DI-контейнер (требует рефакторинга), nock для HTTP (не подходит — qodercli запускается как child_process).

### 4. Отдельный Express-app для тестов без запуска listen
**Решение**: Экспортировать `app` из `server.js` (или создать тестовый helper, собирающий Express-приложение), чтобы supertest мог делать запросы без `app.listen()`.
**Обоснование**: Supertest работает с Express-объектом напрямую, не требуя реального порта. Это быстрее и позволяет параллельное выполнение тестов.
**Альтернативы**: Запуск реального сервера на случайном порту (медленнее, конфликты портов).

### 5. Переменные окружения через process.env в beforeEach
**Решение**: Устанавливать `process.env.PROXY_API_KEY`, `DASHBOARD_PASSWORD` и т.д. в `beforeEach`/`afterEach`, очищать `jest.resetModules()` между тестами.
**Обоснование**: Config.js читает env при первом require. Для тестирования разных конфигураций нужно пересоздавать модуль.
**Риски**: `jest.resetModules()` может быть медленным → использовать selectively.

## Risks / Trade-offs

- **[Риск: config.js кэшируется при require]** → Митигация: `jest.resetModules()` + `jest.isolateModules()` для тестов с разными env-конфигурациями.
- **[Риск: SSE-тесты сложны для парсинга]** → Митигация: парсить SSE-ответ как текст, разбивать по `\n\n`, проверять `data:` строки. Не использовать EventSource в тестах.
- **[Риск: logStore — глобальное состояние]** → Митигация: вызывать `clearRequests()`/`clearSystem()` в `beforeEach` каждого теста.
- **[Риск: dashboardAuth зависит от DASHBOARD_SECRET из config]** → Митигация: мок config модуля или установка env до require.
- **[Trade-off: jest.resetModules замедляет тесты]** → Приемлемо для ~100 тестов; если станет узким местом — перейти к `jest.isolateModules` только где нужно.
