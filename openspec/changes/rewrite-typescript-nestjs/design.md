## Контекст

См. [proposal.md](proposal.md) — мотивация. Текущий проект — ~1500 строк JavaScript в 11 исходных файлах: Express-сервер с 4 модулями маршрутов, 3 middleware, 3 вспомогательными модулями и 1 in-memory хранилищем. Переписывание должно сохранить каждую конечную точку API, форму ответа, поведение стриминга и формат ошибок в точности как есть.

## Цели / Не-цели

**Цели:**
- Типобезопасная кодовая база со строгим TypeScript (`strict: true`)
- Модульная структура NestJS, отражающая текущие логические границы
- Идентичное внешнее поведение API (все конечные точки, стриминг, SSE, форматы ошибок)
- Чистое внедрение зависимостей для конфигурации, вызова qodercli и хранения логов
- Статический фронтенд дашборда отдаётся без изменений

**Не-цели:**
- Добавление новых конечных точек API или функций
- Переписывание фронтенда дашборда (HTML/JS/CSS остаётся как есть)
- Добавление базы данных или персистентного хранилища (in-memory logStore остаётся in-memory)
- Написание unit/integration тестов (становится возможным благодаря этому изменению, но не входит в рамки)
- Изменение имён переменных окружения или добавление новых

## Решения

### 1. Структура модулей NestJS

```
src/
├── main.ts                          # Bootstrap (заменяет server.js)
├── app.module.ts                    # Корневой модуль
├── app.controller.ts                # GET / (корневая информация), GET /health
├── common/
│   ├── guards/
│   │   └── api-key.guard.ts         # Bearer token auth (заменяет middleware/auth.js)
│   ├── middleware/
│   │   └── logger.middleware.ts      # Логирование запросов (заменяет middleware/logger.js)
│   ├── interfaces/
│   │   ├── openai.interfaces.ts     # Типы ChatCompletion, Completion, Model, ToolCall
│   │   └── qoder.interfaces.ts      # Типы QoderMessage, QoderEvent, StreamData
│   └── filters/
│       └── global-exception.filter.ts  # Глобальный обработчик ошибок
├── config/
│   ├── config.module.ts             # ConfigModule.forRoot с валидацией
│   └── configuration.ts             # Типизированная фабрика конфигурации
├── qoder-cli/
│   ├── qoder-cli.module.ts
│   ├── qoder-cli.service.ts         # Хелперы spawn (заменяет helpers/spawn.js)
│   └── qoder-cli.models.ts          # Каталог моделей + карта алиасов (заменяет части format.js)
├── chat/
│   ├── chat.module.ts
│   ├── chat.controller.ts           # POST /v1/chat/completions, GET /v1/chat/completions
│   ├── chat.service.ts              # Построение промпта, оркестрация стриминга
│   └── tool-prompt.util.ts          # Инъекция промпта tool call + парсинг (заменяет toolPrompt.js)
├── completions/
│   ├── completions.module.ts
│   ├── completions.controller.ts    # POST /v1/completions
│   └── completions.service.ts       # Оркестрация стриминга completion
├── models/
│   ├── models.module.ts
│   └── models.controller.ts         # GET /v1/models, POST /v1/embeddings (501), catch-all
├── dashboard/
│   ├── dashboard.module.ts
│   ├── dashboard.controller.ts      # Все маршруты /dashboard/*
│   ├── dashboard.service.ts         # API логики: чат-песочница, статус, конфиг
│   └── guards/
│       └── dashboard-auth.guard.ts  # Cookie-based auth (заменяет dashboardAuth.js)
└── log-store/
    ├── log-store.module.ts
    └── log-store.service.ts         # In-memory логи запросов и системы (заменяет store/logStore.js)
```

**Обоснование**: Каждый модуль NestJS соответствует одной из текущих границ маршрутов/хелперов. Это делает миграцию механической — каждый файл имеет чёткий аналог 1:1 в исходном коде.

**Рассмотренные альтернативы**:
- _Монолитный AppModule_: Проще, но теряет модульную структуру, ради которой используется NestJS.
- _Feature-sliced с общим ядром_: Избыточно для проекта на ~1500 строк.

### 2. Подход к стримингу

Использовать сырой Express `Response` через `@Res()` в контроллерах NestJS для SSE-стриминга. Стандартная обработка ответов NestJS перехватывает response, поэтому стриминг требует явного отказа через `@Res({ passthrough: false })`.

**Обоснование**: Текущая логика стриминга тесно связана с Express `res.write()` / `res.end()`. Декоратор `@Sse()` в NestJS поддерживает только простые паттерны событий и не обрабатывает сложный многофазный стриминг (role chunk → content chunks → tool call chunks → done), необходимый здесь. Прямой доступ через `@Res()` сохраняет полный контроль.

**Рассмотренные альтернативы**:
- _Декоратор `@Sse()` в NestJS_: Слишком ограничен для многофазного SSE с условными типами чанков.
- _Потоковая обработка через RxJS Observable_: Добавляет сложность без выгоды, так как источник данных — дочерний процесс, а не observable-поток.

### 3. Валидация конфигурации

Использовать `@nestjs/config` с фабричной функцией `configuration.ts`, которая читает `process.env` и возвращает типизированный объект. Добавить runtime-валидацию через `class-validator` на классе `EnvironmentVariables` для быстрого падения при отсутствующих/невалидных переменных окружения.

**Обоснование**: Соответствует текущему поведению `config.js` (читает env, применяет defaults, экспортирует объект), добавляя типовую безопасность и валидацию. Текущий код использует `parseInt` с fallback и ручные проверки null — типизированная фабрика сохраняет этот паттерн.

### 4. Стратегия auth guard

Реализовать `ApiKeyGuard` как NestJS guard, применяемый на уровне контроллера для маршрутов `/v1/*`. Guard читает `PROXY_API_KEY` из `ConfigService` и пропускает auth, если не установлен (соответствуя текущему поведению).

**Обоснование**: Guard'ы — это идиоматический эквивалент Express middleware для auth в NestJS. Применение на уровне контроллера (не глобально) соответствует текущему паттерну, где только маршруты `/v1/*` требуют auth.

### 5. Инструментарий сборки

Использовать `@nestjs/cli` (`nest build`) с компилятором `tsc`. Вывод в `dist/`. Конфиг `nest-cli.json` указывает `src/` как корень исходников.

**Обоснование**: `@nestjs/cli` — стандартный инструмент сборки NestJS. Использование `tsc` (не `swc` и не `webpack`) делает сборку простой и предсказуемой для проекта такого размера.

**Рассмотренные альтернативы**:
- _`tsup` или `esbuild`_: Быстрее, но нестандартно для NestJS, возможны проблемы с декораторами и `reflect-metadata`.
- _`swc`_: Быстрее, но добавляет сложность без существенной выгоды на таком масштабе.

### 6. Статические файлы дашборда

Продолжить отдавать `src/dashboard/public/` как статические ресурсы через `@nestjs/serve-static` или Express `express.static` middleware, зарегистрированный в модуле дашборда.

**Обоснование**: Фронтенд (HTML/JS/CSS) вне рамок. Простейший подход — отдавать ту же директорию с того же URL-префикса.

## Риски / Компромиссы

- **[Точность стриминга]** → Логика SSE-стриминга — самая сложная часть кодовой базы. Прямое использование `@Res()` сохраняет полный контроль, но миграция должна тщательно воспроизвести каждый тип чанка, поведение flush и обработку отключения клиента. **Митигация**: Сохранить логику стриминга структурно идентичной; протестировать с реальными IDE-клиентами (Continue, Zed) после миграции.

- **[Время запуска]** → NestJS имеет более медленный холодный старт, чем raw Express, из-за разрешения модулей и рефлексии. **Митигация**: Приемлемо для прокси-сервера, работающего непрерывно. Docker health check `start-period` уже допускает 15 секунд.

- **[Размер бандла]** → NestJS добавляет ~10-15 МБ в `node_modules` по сравнению с текущими ~5 МБ. **Митигация**: Важно только в Docker; образ `node:20-slim` имеет достаточно места.

- **[Риск миграции]** → Переписывание всех файлов за раз — это big-bang изменение без постепенного отката. **Митигация**: Переписывание механическое (отображение 1:1). Хранить старые файлы `src/`, пока новая сборка не проверена, затем удалить. Dockerfile можно обновить для отката на старую точку входа при необходимости во время перехода.

- **[Метаданные декораторов]** → NestJS требует `emitDecoratorMetadata: true` в tsconfig и импорт `reflect-metadata`. Пропуск этого вызывает тихие сбои DI. **Митигация**: Задокументировать в комментариях tsconfig; добавить `import 'reflect-metadata'` в начало `main.ts`.
